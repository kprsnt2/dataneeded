# Dashboard (Phase 6)

A single-page dashboard over the JobAgents SQLite store. **Python standard
library only** — `http.server` + `socketserver.ThreadingHTTPServer`. No FastAPI,
no Flask, no Jinja2, no npm, no build step, no chart library. The repo's
zero-dependency property is preserved.

```bash
python -m jobagents web                      # http://127.0.0.1:8787/
python -m jobagents web --port 8787 --host 127.0.0.1
python -m jobagents web --port 9000 --db data/jobagents.db
python -m jobagents.web --port 8787          # equivalent standalone entry point
```

The server prints its URL, the resolved database path, and the config/backup
directories on startup. `Ctrl-C` stops it.

---

## Design constraints

| Constraint | How it is met |
|---|---|
| Standard library only | `http.server`, `socketserver`, `json`, `sqlite3`, `argparse`, `pathlib`, `re` |
| No build step | One static `jobagents/templates/index.html` with inline CSS + JS |
| No chart library | Inline SVG generated by ~60 lines of vanilla JS |
| Bind to loopback | `--host` defaults to `127.0.0.1` |
| Data via `Store` | Reads go through `Store` (`top_matches`, `source_breakdown`, `job_count`, `pending_drafts`, `recent_runs`) and its `_conn` for aggregate queries |
| Config via `config.py` | The Resume Studio preview calls the real `load_profile()` / `load_keywords()` |
| Handle an empty DB | Every view renders an empty state; verified against a schema-only DB and a missing DB file |

### The single most important property: **there is no send path**

This dashboard is draft-only by design, and that is enforced structurally rather
than promised in a comment:

- No code in `web.py` or `index.html` calls an SMTP client, a mail API, a
  LinkedIn endpoint, or any outbound network function. The only network code in
  the file is the HTTP **server**.
- The `drafts` table has a `sent_at` column. **Nothing in this module ever writes
  it.** Approving a draft sets `status='approved'` and `approved_at` and stops.
- `GET /api/drafts` returns `"send_enabled": false` in its payload, and the UI
  renders that guarantee as a banner.
- `POST /api/drafts/<id>` accepts exactly two actions, `approve` and `reject`. A
  request with `{"action":"send"}` returns `400 unknown action 'send'`.

The Review Queue shows real drafts, real recipients, and real bodies — and its
only two buttons are **Approve draft** and **Reject**.

## Views

The app is one page with five tabs (`#analytics`, `#jobs`, `#studio`, `#review`,
`#runs`). Each tab lazy-loads on first visit.

### 1. Analytics

Eight headline tiles (jobs sourced, matches scored, posted last 7d/30d,
auto-tailor count, pending drafts, best score, sources, score ≥ 40) plus four
charts:

- **Jobs found per day** — last 30 days, grouped on `substr(posted_at,1,10)`.
  Days with no postings are filled with zero so the chart has no gaps. Grouping
  is done on the date text because `posted_at` is an ISO-8601 string with
  heterogeneous UTC offsets and SQLite has no date type here.
- **Score distribution histogram** — all match rows in 10-point buckets, with a
  dashed marker at the configured `auto_tailor` threshold. Bars sum to
  *matches × tracks* because a job is scored once per track; the UI says so.
- **Funnel** — `Sourced → Matched → Auto-tailor → Drafted → Approved`, with each
  stage's conversion percentage against the previous stage:

  | Stage | Definition |
  |---|---|
  | Sourced | `COUNT(*) FROM jobs` |
  | Matched | `COUNT(DISTINCT job_id) FROM matches` |
  | Auto-tailor | `COUNT(DISTINCT job_id) FROM matches WHERE score >= thresholds.auto_tailor` |
  | Drafted | `COUNT(DISTINCT job_id) FROM drafts` |
  | Approved | `COUNT(DISTINCT job_id) FROM drafts WHERE status='approved'` |

  The threshold is read live from `config/keywords.md`, so editing it in the
  Resume Studio moves the funnel and the histogram marker on the next load.
- **Source breakdown** — CSS bars, one row per `source`.
- **Per-track rollup** — table of scored / auto-tailor / best score per track.

### 2. Jobs

Filterable, sortable table: **title, company, location, source, score, posted
date, track, and URL** (the title links out). Filters: min score, track, source,
free-text title/company search, sort order, and row limit.

A job can have up to three match rows (one per track). The table shows the
job's **best-scoring** match unless the `track` filter pins one explicitly —
which is what a human means by "show me my top matches".

Clicking **reasons** expands an inline row showing:

- `reasons_json` verbatim (e.g. `["title=1.00", "keywords=1.00 (7/11)",
  "seniority=senior-title", "location=india", "recency=6d-old"]`)
- the five score components (`title_match`, `keyword_overlap`, `seniority_fit`,
  `location_fit`, `recency`)
- matched keywords (solid chips) and missing keywords (dashed chips)
- all tracks' scores for that job, plus any drafts attached to it
- provenance: job id, `source/external_id`, `dedupe_key`, first/last seen, salary

The empty state tells you what to run: `python -m jobagents source` then
`python -m jobagents match`.

### 3. Resume Studio

A live editor for `config/profile.md` and `config/keywords.md` — the two files
every agent reads.

- The current content loads into a `<textarea>`; **Save (with backup)** POSTs it.
- **The previous version is always written to
  `config/.backups/<name>.<timestamp>.md` before the new content lands.** The
  backup is taken unconditionally on every save of an existing file, and if two
  saves land in the same second the second backup gets a `.1` suffix rather than
  clobbering the first. The file itself is written via a temp file +
  `Path.replace()`, so a crash mid-write cannot leave a truncated config.
- A warning banner states that these files drive all agents: `profile.md` is the
  ground truth the tailor service validates claims against, and `keywords.md`
  sets search terms, matching weights, and thresholds.
- **Parsed structure** panel runs the *real* `load_profile()` / `load_keywords()`
  over the file and shows what the agents will actually see — track count,
  weights, thresholds, metric/skill/rule counts.
- **Save & verify parse** re-parses from disk after the write.
- The **Backups** panel lists `config/.backups/` with sizes and timestamps.
- Unsaved changes are flagged, and `beforeunload` warns before navigating away.

### 4. Review Queue

`pending_drafts()` (i.e. `status='draft'`) rendered as cards with job context,
recipient, subject, body, and the posting link. Each card has **Approve draft**
and **Reject** — and nothing else.

- Approve → `status='approved'`, `approved_at=<utcnow>`, `sent_at` untouched.
- Reject → `status='rejected'`, `approved_at=NULL`, `sent_at` untouched.
- The tab badge shows the pending count.

### 5. Runs

`recent_runs()` as a table: **id, stage, status, started, finished, duration,
stats JSON, errors**. `stats_json` and `errors_json` expand into pretty-printed
`<details>` blocks. Status is colour-coded (`ok` / `partial` / `failed` /
`running`). Duration is computed from the two timestamps, and is `—` while a run
is still running.

## API

All JSON, all `Cache-Control: no-store`. Errors return
`{"ok": false, "error": "..."}` with a real status code.

| Method | Path | Purpose |
|---|---|---|
| GET | `/` | The SPA (`text/html`) |
| GET | `/api/health` | `{"ok":true,"db":...,"db_exists":...,"time":...,"version":...}` |
| GET | `/api/analytics` | Every analytics number. `?days=30` (1–365) |
| GET | `/api/jobs` | Filtered jobs. `?min_score=&track=&source=&q=&sort=&limit=&offset=` |
| GET | `/api/jobs/<id>` | One job + all its matches + its drafts |
| GET | `/api/facets` | Distinct tracks and sources for the filter dropdowns |
| GET | `/api/drafts` | Pending drafts (`status='draft'`) |
| POST | `/api/drafts/<id>` | `{"action":"approve"\|"reject"}` |
| GET | `/api/config/<name>` | `{"name","path","content","bytes","lines","modified_at","backups"}` |
| POST | `/api/config/<name>` | `{"content":"..."}` → backup, then write |
| GET | `/api/parse/<name>` | Parse `config/<name>.md` with the real parsers |
| POST | `/api/parse/<name>` | Parse the **unsaved** editor buffer (no write) |
| GET | `/api/runs` | Recent runs. `?limit=50` (1–500) |

`<name>` is `profile` or `keywords` (a `.md` suffix is accepted). `sort` is one
of `score`, `posted`, `posted_asc`, `title`, `company`, `source`.

### Examples

```bash
curl -s http://127.0.0.1:8787/api/health
curl -s "http://127.0.0.1:8787/api/analytics" | python -m json.tool
curl -s "http://127.0.0.1:8787/api/jobs?min_score=75&limit=5"
curl -s "http://127.0.0.1:8787/api/jobs?track=AI%20Safety%20%2F%20Evaluation%20(NICHE)&min_score=60"
curl -s "http://127.0.0.1:8787/api/jobs?source=remoteok&sort=posted"
curl -s "http://127.0.0.1:8787/api/jobs/3080"
curl -s "http://127.0.0.1:8787/api/drafts"
curl -s -X POST -H "Content-Type: application/json" \
     -d '{"action":"approve"}' http://127.0.0.1:8787/api/drafts/1
curl -s http://127.0.0.1:8787/api/config/profile
curl -s -X POST -H "Content-Type: application/json" \
     -d '{"content":"# edited"}' http://127.0.0.1:8787/api/config/keywords
curl -s http://127.0.0.1:8787/api/runs
```

## Security

**Loopback by default.** `--host` defaults to `127.0.0.1`. Binding elsewhere is
an explicit opt-in.

**Config writes cannot leave `config/`.** `resolve_config()` applies three
independent guards before any write:

1. **Exact-match allow-list** — only the literal names `profile` and `keywords`
   (optionally `.md`, case-insensitive). A name containing `/`, `\`, or `..` is
   rejected outright, so `profile/../keywords` is refused even though it would
   resolve to a legitimate file.
2. **Resolved-path containment** — `Path.resolve()` collapses `..`, symlinks, and
   Windows 8.3 aliases, and the result must be `relative_to(CONFIG_DIR)`.
3. **Must be an existing regular file** inside `config/`.

Verified rejected: `../../etc/passwd`, `profile/../keywords`, `..%2f..%2fsecret`,
`%2e%2e%2fconfig%2fprofile`, `profile%00.md`, `profile.md.exe`,
`C:\Windows\win.ini`, `....//keywords`, empty names, and off-list names.

> **Testing note.** `curl.exe` normalises `/api/config/profile/../keywords` into
> `/api/config/keywords` *on the client* before sending, so a naive traversal
> probe silently hits a real endpoint and really writes. Use `curl --path-as-is`
> to test what the server actually does with a traversal path.

**Other hardening.** Read-only by default — the only writes in the whole module
are the draft status update and the config save. No path is derived from
user input except through the allow-list above. `sqlite3` values are always
parameterised. Threading uses one `Store` (one connection) per request, since
`sqlite3` connections are not shareable across threads. The request handler
catches every exception and returns JSON rather than killing a worker thread.

## Verified behaviour

Measured against the live database (7,546 jobs, 22,120 match rows, 10 sources,
12 runs) on Python 3.11:

| Check | Result |
|---|---|
| All endpoints, real data | 200 with real rows |
| Concurrent load (12 threads × 8 requests) | 96/96 returned 200, no errors |
| Empty DB (schema only, 0 rows) | all endpoints 200, sane empty payloads |
| Missing DB file | schema created on connect, all endpoints 200 |
| Config save → backup → restore | backup byte-identical to the original; restore byte-exact |
| 10 traversal probes | all rejected, no file mutated |
| Malformed input (bad JSON, bad types, bad params) | 4xx, never 5xx |
| SQL-injection-shaped `sort` parameter | ignored; `PRAGMA integrity_check` → `ok` |
| External network resources in the page | none |

### Limitations

- **Single-process, no auth.** Anyone who can reach the port has full control,
  including config writes. This is why it binds to loopback; do not expose it.
- **Read-only on the pipeline.** The dashboard observes runs but cannot start
  one. Trigger `source` / `match` from the CLI.
- **`posted_at` grouping is textual.** Dates are grouped on `substr(posted_at,1,10)`
  rather than parsed, because stored offsets vary. Correct for the ISO-8601
  values the sources emit; a non-ISO value would fall into whatever bucket its
  first ten characters imply.
- **Funnel "Drafted" counts jobs, not drafts.** One job with two drafts counts
  once, which is the intended reading of the funnel.
- **No pagination control in the UI.** The table caps at the selected limit
  (default 100); the API supports `offset` but the UI does not expose it.
- **The jobs table's best-match join can surface a duplicate** when two tracks
  produce the identical top score for one job. Cosmetic only.
- **Analytics recomputes on every load.** At ~22k match rows this is a few
  milliseconds; it is not cached.
